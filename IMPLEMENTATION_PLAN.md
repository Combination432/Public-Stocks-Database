# US Financial Statement Database - Implementation Plan

## Technology Stack

### Backend
- **Language**: Python 3.11+
- **Web Framework**: FastAPI (high performance, async support, automatic API docs)
- **Database**: PostgreSQL 15+ (reliable, excellent JSON support, ACID compliance)
- **ORM**: SQLAlchemy 2.0 (type-safe, async support)
- **Task Queue**: Celery + Redis (for ETL pipeline scheduling)
- **EDGAR Access**: SEC-API or custom parser using `requests` + `lxml`/`BeautifulSoup`
- **XBRL Parsing**: `python-xbrl` or `Arelle`

### Frontend
- **Framework**: React 18+ with TypeScript
- **UI Library**: Material-UI or Tailwind CSS
- **State Management**: React Query (for API data fetching/caching)
- **Export**: `xlsx` library for Excel export

### Infrastructure
- **Containerization**: Docker + Docker Compose
- **Database Migrations**: Alembic
- **API Documentation**: OpenAPI/Swagger (auto-generated by FastAPI)
- **Testing**: pytest, pytest-asyncio
- **Linting**: ruff, black, mypy

## Implementation Phases

### Phase 1: Foundation (Days 1-2)
**Goal**: Set up project infrastructure and database

1. **Project Setup**
   - Create directory structure
   - Initialize Git repository
   - Set up Docker Compose (PostgreSQL, Redis, backend, frontend)
   - Create environment configuration

2. **Database Implementation**
   - Write SQL schema with indexes
   - Set up Alembic migrations
   - Create SQLAlchemy models
   - Add data validation constraints

3. **Testing Infrastructure**
   - Set up pytest
   - Create test database fixture
   - Write initial model tests

**Deliverable**: Working database with migrations, containerized environment

### Phase 2: ETL Pipeline - Core Parser (Days 3-5)
**Goal**: Build the data extraction and parsing logic

1. **SEC EDGAR Integration**
   - Implement company list retrieval (CIK lookup)
   - Build filing RSS/Atom feed monitor
   - Create filing downloader (respect rate limits)
   - Implement filing metadata extraction

2. **XBRL Parser**
   - Parse XBRL instance documents
   - Identify statement contexts (IS, BS, CF)
   - Extract line items with labels
   - Preserve statement order
   - Handle multiple presentation linkbases

3. **Data Transformer**
   - Clean and normalize numerical values
   - Extract "as-reported" line item names
   - Map to database schema
   - Handle restatements (upsert logic)

4. **Data Validator**
   - Implement balance sheet equation check
   - Detect missing/malformed data
   - Log validation errors

**Deliverable**: Parser that can process a single 10-K/10-Q and load into DB

### Phase 3: ETL Pipeline - Automation (Days 6-7)
**Goal**: Automate continuous monitoring and historical backfill

1. **Celery Task Queue**
   - Set up Celery workers
   - Create periodic tasks (check for new filings every hour)
   - Implement retry logic with exponential backoff
   - Add logging and monitoring

2. **Backfill Script**
   - Retrieve 10 years of historical filings
   - Batch processing with concurrency control
   - Progress tracking
   - Resume capability (idempotent)

3. **Company Universe Management**
   - Fetch active tickers from NASDAQ, NYSE, NYSE American
   - Store in Company table
   - Periodic refresh

**Deliverable**: Automated ETL pipeline with historical data loaded

### Phase 4: RESTful API (Days 8-10)
**Goal**: Build production-ready API

1. **Core Endpoints**
   - `GET /company/{ticker}` - Company metadata
   - `GET /filings/{ticker}` - List filings

   - `GET /data_point/{ticker}/{line_item_name}` - Time series

2. **API Infrastructure**
   - API key authentication middleware
   - Rate limiting
   - Request validation (Pydantic)
   - Error handling (standardized responses)
   - CORS configuration
   - Response caching (Redis)

3. **Performance Optimization**
   - Database query optimization (explain analyze)
   - Add indexes on ticker, filing_date, line_item_name
   - Implement pagination for large responses
   - Connection pooling

4. **API Documentation**
   - OpenAPI/Swagger UI
   - Request/response examples
   - Authentication guide

## Key Technical Decisions

### 1. XBRL vs HTML Parsing
- **Primary**: XBRL (structured, machine-readable)
- **Fallback**: HTML parsing for older filings
- Most filings since 2009 are XBRL-based

### 2. Line Item Name Handling
- Store exact "as-reported" string (no normalization per spec)
- Case-sensitive storage
- URL-encode for API requests
- Future: maintain separate mapping table (out of V1 scope)

### 3. Restatement Strategy
- Use `ON CONFLICT` (upsert) based on (company_id, period_year, period_quarter, statement_type, line_item_name)
- Most recent filing_date wins
- Consider adding `is_restatement` flag for audit trail

### 4. Performance Targets
- Database indexing strategy:
  - `Company(ticker)` - UNIQUE INDEX
  - `Filing(company_id, filing_date)` - INDEX
  - `FinancialData(filing_id, statement_type)` - INDEX
  - `FinancialData(line_item_name)` - INDEX (for time series queries)
- Query optimization: Use EXPLAIN ANALYZE
- Caching: Redis for frequently accessed data (e.g., latest statements)

### 5. Data Validation Rules
- Balance Sheet: `Assets = Liabilities + Equity` (within 0.01% tolerance)
- Cash Flow: Verify reconciliation (if reported)
- Income Statement: Revenue >= 0 for most companies
- Log violations without blocking (data quality dashboard)

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| XBRL parsing complexity | High | Use established libraries (Arelle), extensive testing |
| SEC rate limiting | Medium | Implement exponential backoff, respect guidelines |
| Data volume (10 years) | Medium | Batch processing, resume capability |
| Statement format variations | High | Flexible parser, manual QA on diverse samples |
| API performance | High | Caching, indexing, query optimization |
